# 09 — Execution Plan (Superpowers)

Ten phases, each independently shippable, each ending with something you can use. The
ordering has one governing rule:

> **You must be using the app as your daily driver before you build the next thing.**

Personal projects don't fail on technology. They fail by staying unusable long enough that
you stop caring. Every phase below ends with a version that replaces something you're
currently paying for.

---

## 1. The operating loop

Each phase runs the same cycle. This is the Superpowers workflow applied to this project.

```
┌─ 1. DESIGN ─────────────────────────────────────────────────┐
│  superpowers:brainstorming                                   │
│    → questions, 2–3 approaches, sectioned design             │
│    → docs/superpowers/specs/YYYY-MM-DD-<phase>-design.md     │
│    → you review and approve the spec                         │
└──────────────────────────────────────────────────────────────┘
                              ▼
┌─ 2. PLAN ───────────────────────────────────────────────────┐
│  superpowers:writing-plans                                   │
│    → docs/superpowers/plans/YYYY-MM-DD-<phase>-plan.md       │
│    → task-by-task, with verification steps                   │
└──────────────────────────────────────────────────────────────┘
                              ▼
┌─ 3. ISOLATE ────────────────────────────────────────────────┐
│  superpowers:using-git-worktrees                             │
│    → a worktree per phase; main stays installable            │
└──────────────────────────────────────────────────────────────┘
                              ▼
┌─ 4. EXECUTE ──────────── (fresh session, clean context) ────┐
│  superpowers:executing-plans        ← sequential, w/ gates   │
│    or superpowers:subagent-driven-development  ← independent │
│    or superpowers:dispatching-parallel-agents  ← 2+ parallel │
│                                                              │
│  every task: superpowers:test-driven-development             │
│  when stuck: superpowers:systematic-debugging                │
└──────────────────────────────────────────────────────────────┘
                              ▼
┌─ 5. VERIFY ─────────────────────────────────────────────────┐
│  superpowers:verification-before-completion                  │
│    → run the commands, paste the output, no claims w/o proof │
└──────────────────────────────────────────────────────────────┘
                              ▼
┌─ 6. REVIEW ─────────────────────────────────────────────────┐
│  superpowers:requesting-code-review  (or /code-review high)  │
│  superpowers:receiving-code-review   ← verify before obeying │
│  /simplify for quality-only cleanup                          │
└──────────────────────────────────────────────────────────────┘
                              ▼
┌─ 7. INTEGRATE ──────────────────────────────────────────────┐
│  superpowers:finishing-a-development-branch                  │
│    → merge, install on device, tag the version               │
└──────────────────────────────────────────────────────────────┘
```

**Three habits that make this work:**

- **Fresh session for execution.** Design and planning fill context with exploration.
  Executing a plan wants a clean session that reads the plan file and works.
- **`/init` after Phase 0.** Once the stack is chosen, generate `CLAUDE.md` so every future
  session starts knowing the conventions, the commands, and the layout. Update it each phase.
- **The plan file is the interface.** If a plan is good, execution is mechanical and you can
  hand it to a subagent or pick it up three weeks later.

## 2. Repo layout

```
health-app/
├── docs/                       ← these documents (research, stable)
│   ├── 01-…-10-…md
│   └── superpowers/
│       ├── specs/              ← per-phase designs from brainstorming
│       └── plans/              ← per-phase implementation plans
├── core/                       ← PURE LOGIC. no framework imports. heavily tested.
│   ├── energy/                 ← Kalman filter, TDEE, targets, macros
│   ├── training/               ← e1RM, volume, PRs, progression
│   ├── nutrition/              ← portions, recipe scaling, Atwater checks
│   ├── sync/                   ← conflict resolution, outbox reconciliation
│   └── insights/               ← the cross-domain analyses
├── db/
│   └── migrations/             ← raw SQL, numbered, forward-only
├── app/                        ← the UI. stack-dependent, decided in Phase 0.
├── health/                     ← HealthGateway + two platform implementations
├── pipeline/                   ← food data ingestion scripts (laptop-side)
├── backend/                    ← Supabase schema, policies, functions
└── CLAUDE.md                   ← generated by /init after Phase 0
```

**`core/` is the most important directory in the project.** It has no framework imports, no
UI types, no database types, no I/O. Pure functions over plain data. That makes it the most
testable code you'll write, the most valuable, and the only part that survives a change of
stack ([doc 03](03-cross-platform-approaches.md) §4).

## 3. The phases

### Phase 0 — Stack spike ⟶ *a decision*

**Goal:** close the stack question with evidence.
**Superpowers path:** brainstorming **spike** path — output is an answer, not code you keep.

Build the vertical slice from [doc 03](03-cross-platform-approaches.md) §3 in **two** stacks
(recommended: Flutter and React Native + Expo). Timebox **2–3 days each, hard stop.**

- Slice: 3 exercises × 4 set rows with inline inputs, previous column, tap-to-autofill,
  backgrounded rest timer, immediate SQLite persistence, one health-store write, one chart.
- Get it onto a **real device via the real channel** — TestFlight and a sideloaded APK.
- Score against the written acceptance criteria. Don't move the goalposts mid-spike.

**Gate:** a written recommendation with evidence. All spike code is labelled throwaway and
deleted.
**Then:** `/init` to generate `CLAUDE.md`.
**Blocks:** everything.

---

### Phase 1 — Foundation ⟶ *an empty app on your phone*

**Goal:** the boring infrastructure, done once, done properly.

- Repo scaffold in the chosen stack; lint, format, typecheck, test runner
- SQLite wired up, WAL, foreign keys; the full schema from
  [doc 06](06-data-architecture.md) §3 as migration `0001_initial.sql`
- Migration runner with **copy-before-migrate**
- CI: test → build both platforms → TestFlight + APK artifact
  ([doc 04](04-productionization-and-deployment.md) §3)
- Apple Developer enrolment, signing, Android keystore (**backed up somewhere safe**)
- A tab shell with five empty screens

**Definition of done:** you push to `main` and 15 minutes later a build with an empty UI is
on both phones. Every table exists and is empty.

*Boring, and skipping it means hand-building every release for a year.*

---

### Phase 2 — Domain core ⟶ *the crown jewels*

**Goal:** every algorithm in the app, as pure tested functions, before any UI exists.

**This is the highest-leverage phase and the best fit for parallel agents** — the modules
share nothing but plain data types.

| Module | Contents | Source |
|---|---|---|
| `core/energy` | Kalman filter (weight + expenditure), trend weight, target generation, macro allocation, guardrails, phase-change noise handling | [doc 02](02-calorie-trackers-breakdown.md) §2–3 |
| `core/training` | e1RM (Brzycki), volume, per-muscle set counts, PR detection incl. the rep-max table | [doc 01](01-strong-app-breakdown.md) §4 |
| `core/nutrition` | per-100g scaling, portion parsing, recipe scaling with cooked yield, Atwater validation | [doc 07](07-food-database.md) §6–8 |
| `core/sync` | conflict resolution, outbox reconciliation, cursor handling | [doc 06](06-data-architecture.md) §4 |

**Skills:** `superpowers:dispatching-parallel-agents` (four independent modules) with
`superpowers:test-driven-development` inside each.

**Test the Kalman filter properly — this is the one that matters:**

1. **Synthetic ground truth.** Generate 180 days with a known true TDEE and known intake, add
   realistic scale noise (σ ≈ 0.9 kg). The filter must recover the true TDEE within ~5% by
   day 30. This is the acceptance test.
2. **Missing data.** Skip 40% of weigh-ins randomly. Skip whole weeks of intake. It must
   degrade gracefully and widen its uncertainty rather than producing garbage.
3. **Step change.** True TDEE jumps 300 kcal at day 90. It must track within ~3 weeks.
4. **The glycogen trap.** Simulate 1.5 kg of water loss in week 1. It must *not* conclude
   your TDEE is 4,000.
5. **Constant under-reporting.** Log 85% of true intake throughout. Assert the *prescribed
   deficit* is still correct even though the absolute estimate is biased
   ([doc 02](02-calorie-trackers-breakdown.md) §2).
6. **Guardrails.** Adversarial inputs must never produce a target below the floor.

**Definition of done:** `core/` has no framework imports, tests pass, and you can run the
filter over synthetic data from a CLI and see sensible numbers.

### Phase 3 — Training ⟶ **v0.1**, and Strong gets deleted

**Goal:** replace Strong completely.

- Exercise library, seeded (~200 common exercises) + custom exercises
- Routines: create, edit, reorder, folders, supersets
- **The active workout screen** ([doc 01](01-strong-app-breakdown.md) §2) — this is the
  phase's centre of gravity and deserves most of its budget
- Rest timer with backgrounding: iOS Live Activity, Android foreground service
- History: calendar, workout detail, per-exercise history, PRs
- **Strong CSV importer** — do this early in the phase, not late
- JSON export

**Skills:** `superpowers:executing-plans` sequentially. The logging screen is not a good
parallel-agent candidate — it's one tightly-coupled interaction surface.

**Gate — a real one, not a checkbox:** use it for **every session for two weeks** without
opening Strong. If you reach for Strong, the phase isn't done. Fix what made you reach.

---

### Phase 4 — Nutrition ⟶ **v0.2**, and MacroFactor gets deleted

**Goal:** replace MacroFactor's logging (not yet its algorithm).

Two independent tracks — **run them in parallel**:

**4a — Data pipeline** (laptop-side scripts, no app code)
- USDA Foundation + SR Legacy + FNDDS → normalized → FTS5 → bundled `core.sqlite`
- Quality gate, Atwater validation, portion extraction
- Emits a versioned artifact the app ships with

**4b — App**
- Food search (local FTS + personal-history ranking)
- Barcode scan → OFF public API → **permanent local cache**, with the UPC/EAN handling from
  [doc 07](07-food-database.md) §4
- Custom foods, recipes with cooked yield, saved meals, quick-add
- Diary with meal sections, copy-previous-day, learned portions
- Manual weigh-in

**Optional 4c (defer until proven necessary):** self-hosted OFF mirror. Only if you hit rate
limits, want offline scanning, or need brand search
([doc 07](07-food-database.md) §2).

**Gate:** log every day for two weeks without opening MacroFactor. Targets are still manual.

---

### Phase 5 — The algorithm ⟶ **v0.3**

**Goal:** wire Phase 2's `core/energy` to real data and real screens.

- Trend weight chart with raw weigh-ins behind it
- Expenditure chart **with its uncertainty band**
- Weekly check-in screen ([doc 08](08-combined-app-design.md) §3) — the ritual
- Target generation, three coaching modes, guardrails
- Diet phases, with phase-change noise handling in the filter

**Validation before you trust it:** run the filter over your *imported historical data* and
sanity-check the output against what you know actually happened during past cuts. This is
the only real test, and it's the reason the importers were built in Phases 3 and 4.

**Gate:** a full week's targets generated automatically, and you believe them.

---

### Phase 6 — Health integrations ⟶ **v0.4**

**Goal:** stop typing your bodyweight in.

- `HealthGateway` interface ([doc 05](05-health-integrations.md) §5)
- **HealthKit implementation** — anchored queries, background delivery, correlations, sync
  identifiers
- **Health Connect implementation** — Changes API, permissions incl. history + background,
  rationale activity, `clientRecordId`
- Ingest bodyweight, steps, active energy, external workouts
- Write nutrition and workouts back, with source filtering to prevent loops

**Parallelize:** the two implementations are independent behind the interface. Two worktrees,
two agents. Write the interface and the fake first, and the layer above it against the fake.

**Gate:** step on a smart scale; the trend and the expenditure estimate update without you
opening the app.

---

### Phase 7 — Sync and backup ⟶ **v0.5**

**Goal:** the data outlives the phone.

- Supabase project, schema, RLS, magic-link auth
- `server_seq` sequence + triggers ([doc 06](06-data-architecture.md) §4)
- Client: outbox push, cursor pull, LWW resolution, tombstones, `cursor_too_old` handling
- Automated weekly versioned export to iCloud Drive / Google Drive
- **A tested restore path** — restore into a clean install and verify

**Gate:** install on a second device, sign in, and watch a decade of data arrive. Then wipe
one device and restore from backup alone.

---

### Phase 8 — Insights ⟶ **v1.0**, the reason you built this

**Goal:** the nine cross-domain analyses from [doc 08](08-combined-app-design.md) §1.

Each is an independent card over data that already exists — **ideal parallel-agent work,
one agent per insight**, each with its own tests over fixture datasets.

1. Strength vs diet phase overlay
2. Training volume ↔ expenditure regression
3. Recomp detection
4. Relative strength / DOTS over time
5. Plateau attribution
6. Fuelling check (training vs rest day intake)
7. Fatigue and deload signals
8. Bodyweight-corrected volume
9. The unified weekly check-in

**Rule: every insight must degrade honestly.** Not enough data means saying so, not
extrapolating from three points. Write that test first for each card.

**Gate:** the check-in tells you something you didn't already know.

---

### Phase 9 — Public release (optional, much later)

Only if you decide to. Everything in
[doc 04](04-productionization-and-deployment.md) §4: privacy manifests, nutrition labels,
Data Safety, Health Connect declaration, privacy policy, account deletion, medical
disclaimer, and the Play closed-testing wall.

**Start the long-lead items early** — Play's 12-testers-for-14-days requirement and the
Health Connect declaration are wall-clock waits, not work.

## 4. What to parallelize

| Phase | Parallel? | How |
|---|---|---|
| 0 Spike | ✅ | Two stacks, two worktrees, same slice, same criteria |
| 1 Foundation | ❌ | Everything depends on it |
| 2 Domain core | ✅✅ | Four independent modules — the best parallel opportunity in the project |
| 3 Training | ❌ | One tightly-coupled interaction surface |
| 4 Nutrition | ✅ | Pipeline (4a) ∥ app (4b) |
| 5 Algorithm | ❌ | Small, sequential, needs judgement |
| 6 Health | ✅ | HealthKit ∥ Health Connect, behind one interface |
| 7 Sync | ❌ | Correctness-critical; one careful pass beats three fast ones |
| 8 Insights | ✅✅ | One agent per insight card |

**When parallelizing, use `superpowers:dispatching-parallel-agents` with
`superpowers:using-git-worktrees`** so agents can't collide on files. Give each agent a spec
with explicit interfaces so the merge is mechanical.

A "session" is 2–4 focused hours. At three sessions a week, **v0.1 lands around month three
and v1.0 around month seven.** Adjust for your actual life; the ordering matters more than
the numbers, because every phase from 3 onward ends with something you'd genuinely use.

## 6. Session hygiene

Things that make agent-assisted work on a long project go well:

1. **One phase per worktree, one plan per phase.** Never two phases in flight.
2. **Design and execute in different sessions.** Different context needs.
3. **Keep `CLAUDE.md` current** — stack, commands, conventions, gotchas. It's what stops
   every session relearning the project.
4. **`superpowers:verification-before-completion` before any "done".** Run the command,
   read the output, then claim it.
5. **`/code-review high` before merging each phase.** Cheap, and it catches the sync and
   migration bugs that are expensive later.
6. **`superpowers:systematic-debugging` the moment something is confusing.** Guess-and-check
   debugging on a Kalman filter or a sync engine will eat a whole weekend.
7. **Commit the specs and plans.** They're the record of *why*, and in nine months that's
   worth more than the diff.
8. **Never skip the daily-driver gates.** They're the mechanism that stops this becoming a
   70%-finished project.

## 7. Start here

The next three things, in order:

1. **Read [doc 10](10-decisions-log.md)** and answer the open questions — a few of them
   change Phase 0.
2. **Run Phase 0.** Invoke `superpowers:brainstorming`, take the **spike** path, build the
   vertical slice in two stacks, decide with evidence.
3. **`/init`** to write `CLAUDE.md`, then start Phase 1.

Do not start Phase 1 before Phase 0 is decided. Do not start Phase 4 before you've used
v0.1 for two weeks. The ordering is the plan.
